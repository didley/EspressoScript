The problem

Too many ways to write the same thing.

TypeScript lets you declare variables three ways, write functions four ways, handle errors five ways. Reading unfamiliar code is hard. Code review is harder. LLM-assisted generation amplifies every inconsistency — more valid forms means more ways to generate subtly wrong code.

ShotScript's answer: a strict lint pass, a formatter, and a tsconfig that enforce one canonical form. Your TypeScript files are unchanged — we maintain a list of rules, not a compiler.
no-throw / no-try
Errors are values — return PromiseResult<T, E> tuples. Failure is in the type signature, not the air.
no-undefined-type / no-optional-property
null is the only absent value. No ?, no | undefined — one way to say "nothing."
require-readonly-property / require-readonly-arrays
Every field and array is readonly by default. Mutation is opt-in and explicit.
no-any / no-assertion / no-non-null
Type safety is not optional. any, as, !, and @ts-ignore are all banned.
no-class / no-this
Plain type + plain functions. No hidden state, no inheritance, no this.
no-arrow-functions
Every function is named and grep-able. Callbacks become testable, findable units.
no-interface / no-enum
One way to define a shape: type. No parallel declaration syntax.
no-ternary
If/else forces names onto branches. Nesting disappears.
What is ShotScript

Four tools. One package.

ShotScript is not a language or a compiler. It's a set of tools that constrain TypeScript to a single canonical form.

ShotScriptLint
95+ rules enforcing one way of doing things, compile-time enforced.
ShotScriptFmt
Formatting optimised for minimim diffs, and terminal previews.
ShotScriptTyping
The strict settings TypeScript recommends but can't enable by default.
ShotScriptStd
Safe, non-throwing utils. The primitives the rules require.
ShotScript
Is it for you?

Not a linter. Almost a language.

ShotScript's constraint set is comprehensive enough that valid code looks nothing like typical TypeScript. No classes, no arrow callbacks, no ternaries, no throw, no raw Promises — not because these features are bad, but because having one canonical form is the point. Think of it less as "stricter TypeScript" and more as a dialect: TypeScript provides the type system and toolchain; ShotScript defines a narrower syntax within it.

Designed for greenfield. ShotScript is for teams who want a single, non-negotiable way to write typed JavaScript from day one — not for incrementally hardening an existing codebase.
Existing codebases
Rules like no-class, no-promise, and no-arrow-functions require architectural rewrites, not search-and-replace. There is no gradual migration path.
Class-based frameworks
Angular, NestJS, and similar frameworks are built around classes, constructors, and decorators — constructs ShotScript bans outright.
Rule-by-rule opt-in
There is no config surface. The rules are interdependent: no-throw only makes sense once you have PromiseResult; require-async-tuple-return only makes sense once raw Promises are gone.

What the simplifications look like.

Real patterns. The left column is TypeScript as commonly written; the right column is the ShotScript equivalent.

Error handling

TypeScript 
async function getUser(
  id: number
): Promise<User> {
  try {
    const res = await fetch(`/users/${id}`)
    if (!res.ok) throw new Error(
      `HTTP ${res.status}`
    )
    return res.json() as User
  } catch (e) {
    throw new Error(`getUser failed: ${e}`)
  }
}
ShotScript 
import { safeFetch, jsonParse } from 'shotscript/std'
import type { PromiseResult } from 'shotscript/std'

async function getUser(
  id: number
): PromiseResult<User> {
  const [res, err] = await safeFetch(`/users/${id}`)
  if (err !== null) {
    return [null, err]
  }
  return jsonParse<User>(await res.text())
}

// no throw · no try · no hidden control flow
Why it matters: thrown exceptions don't appear in function signatures. Callers have no idea a function can fail without reading its source. PromiseResult<T, E> makes every failure path explicit in the type, enforced by the checker.

Absent values

TypeScript 
// three ways to say "nothing"
type User = {
  id: number
  avatar?: string
  deletedAt?: Date
}

function findUser(
  id?: number
): User | undefined { /* ... */ }
ShotScript 
// one way — null is the only absent value
type User = {
  readonly id: number
  readonly avatar: string | null
  readonly deletedAt: Date | null
}

function findUser(
  id: number
): [User | null, Error | null] { /* ... */ }
Why it matters: TypeScript has three ways to express "this might not exist" — ?, | undefined, and | null — and most codebases mix all three. ShotScript picks one: null. Every optional field is T | null, every fallible return is [T | null, Error | null]. No more checking for both.

Type complexity

TypeScript 
// intersection to "extend" a base type
type User = {
  readonly id: number
  readonly name: string
}

type AdminUser =
  User & { readonly role: 'admin' }

// what fields does AdminUser have?
// depends on what User is today
ShotScript 
// embed as a named field — Go/Rust-style
type User = {
  readonly id: number
  readonly name: string
}

type AdminUser = {
  readonly user: User
  readonly role: 'admin'
}

// access: admin.user.id
Why it matters: intersection types hide fields behind indirection. ShotScript bans &, conditional types, mapped types, and infer. Instead of extending, embed: give the base type a named field. Every shape is self-contained and readable where it's defined.

Immutable by default

TypeScript 
type Config = {
  host: string
  port: number
}

const ids: number[] = []

// any function can mutate these
// nothing in the types stops it
ShotScript 
type Config = {
  readonly host: string
  readonly port: number
}

const ids: readonly number[] = []

// compiler rejects any write to these
Why it matters: mutable data structures mean any function, at any call site, can change state you didn't expect. readonly makes the compiler enforce immutability — mutation becomes opt-in, visible, and intentional.

Data + behaviour

TypeScript 
class UserService {
  private readonly db: Database

  constructor(db: Database) {
    this.db = db
  }

  async findById(
    id: number
  ): Promise<User | null> {
    // ...
  }
}

const svc = new UserService(db)
ShotScript 
type UserService = { readonly db: Database }

async function findUserById(
  svc: UserService,
  id: number,
): Promise<[User | null, Error | null]> {
  // ...
}

const svc: UserService = { db }
Why it matters: a type is data. A function is behaviour. There is no hidden state, no inheritance graph to trace, no this context to reason about. Both are independently testable.

Callbacks

TypeScript 
const total = items
  .filter(x => x.active)
  .map(x => ({ ...x, score: x.score * 2 }))
  .reduce((acc, x) => acc + x.score, 0)

// inline logic · untestable · no names to grep
ShotScript 
function isActive(item: Item): boolean {
  return item.active
}
function doubleScore(item: Item): Item {
  return { ...item, score: item.score * 2 }
}
function sumScore(acc: number, item: Item): number {
  return acc + item.score
}

const total = items
  .filter(isActive)
  .map(doubleScore)
  .reduce(sumScore, 0)
Why it matters: named functions are testable in isolation, searchable with grep, and show up in stack traces. Anonymous arrow callbacks disappear the moment they fail.

Conditionals

TypeScript 
const label = isAdmin
  ? (isSuperAdmin ? "Super Admin" : "Admin")
  : "User"

// nesting grows with every new role
ShotScript 
function roleLabel(
  isAdmin: boolean,
  isSuperAdmin: boolean,
): string {
  if (isSuperAdmin) {
    return "Super Admin"
  }
  if (isAdmin) {
    return "Admin"
  }
  return "User"
}
Why it matters: each branch has a name. Adding a new role means adding a clause, not untangling a nested expression. The complexity stays flat.
Install

One package. Four tools.

$ npm install --save-dev shotscript
ShotScriptLint — tsconfig plugin 
// tsconfig.json
{
  "compilerOptions": {
    "plugins": [{ "name": "shotscript/plugin" }]
  }
}
ShotScriptFmt — biome config 
// biome.json
{
  "extends": ["shotscript/fmt"]
}
ShotScriptTyping — tsconfig strict mode 
// tsconfig.json
{
  "extends": "shotscript/tsconfig/shotscript.json"
}
ShotScriptStd — stdlib import 
import { safeFetch, jsonParse } from 'shotscript/std'
import type { Result, PromiseResult } from 'shotscript/std'
