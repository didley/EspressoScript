The problem

Too many ways to write the same thing.

TypeScript lets you declare variables three ways, write functions four ways, handle errors five ways. Reading unfamiliar code is hard. Code review is harder. LLM-assisted generation amplifies every inconsistency — more valid forms means more ways to generate subtly wrong code.

5 error patterns — throw, try/catch, rejected Promise, error-first callback, return tuple → PromiseResult<T>
3 ways to say "nothing" — ?, | undefined, | null → | null
4 function forms — arrow, declaration, expression, method → function f() {}
3 type-shape constructs — type, interface, class → type T = {}
ShotScript removes ~79% of TypeScript's ways to write the same thing and standardises the rest to one. Your files are unchanged — it's a list of rules, not a compiler.
no-throw / no-try
Errors are values — return PromiseResult<T, E> tuples. Failure is in the type signature, not the air.
no-undefined-type / no-optional-property
null is the only absent value. No ?, no | undefined — one way to say "nothing."
require-readonly-property / require-readonly-arrays
Every field and array is readonly by default. Mutation is opt-in and explicit.
no-any / no-assertion / no-non-null
Type safety is not optional. any, as, !, and @ts-ignore are all banned.
no-class / no-this
Plain type + plain functions. No hidden state, no inheritance, no this.
no-arrow-functions
Every function is named and grep-able. Callbacks become testable, findable units.
no-interface / no-enum
One way to define a shape: type. No parallel declaration syntax.
no-intersection-types
& is banned. Spell every field out directly — flat types are fully readable where they're defined, with no hidden merges to untangle.
no-ternary
If/else forces names onto branches. Nesting disappears.
What is ShotScript

Five tools. One package.

ShotScript is not a language or a compiler. It's a set of tools that constrain TypeScript to one way of doing things.

ShotScriptLint
95+ rules enforcing one way of doing things, compile-time enforced.
ShotScriptFmt
Formatting optimised for minimim diffs, and terminal previews.
ShotScriptTyping
The strict settings TypeScript recommends but can't enable by default.
ShotScriptStd
Safe, non-throwing utils. The primitives the rules require.
ShotScriptSkills
Claude Code commands — fix, migrate, and explain violations on demand.

Is it for you?

Not a linter. Almost a language.

ShotScript's constraint set is comprehensive enough that valid code looks nothing like typical TypeScript. No classes, no arrow callbacks, no ternaries, no throw, no raw Promises — not because these features are bad, but because having one way of doing things is the point. Think of it less as "stricter TypeScript" and more as a dialect: TypeScript provides the type system and toolchain; ShotScript defines a narrower syntax within it.

Designed for greenfield. ShotScript is for teams who want a single, non-negotiable way to write typed JavaScript from day one — not for incrementally hardening an existing codebase.
Existing codebases
Rules like no-class, no-promise, and no-arrow-functions require architectural rewrites, not search-and-replace. There is no gradual migration path.
Class-based frameworks
Angular, NestJS, and similar frameworks are built around classes, constructors, and decorators — constructs ShotScript bans outright.
Rule-by-rule opt-in
There is no config surface. The rules are interdependent: no-throw only makes sense once you have PromiseResult; require-async-tuple-return only makes sense once raw Promises are gone.
Before / after

Same logic. Fewer states.

Three real examples — types, async, and stateful services — shown as commonly written TypeScript and as ShotScript with every rule applied.

Type structure

TypeScript 
type Role = 'admin' | 'member' | undefined

interface Timestamps {
  createdAt: Date
  updatedAt?: Date
}

interface BaseUser {
  id: number
  email: string
  avatar?: string | null
  metadata?: Record<string, any>
}

type User = BaseUser & Timestamps & {
  role?: Role
  deletedAt?: Date | null
}

// 4 ways to say "nothing" · 8 states for `role`
// fields are merged invisibly across 3 decls
ShotScript 
type Role = 'admin' | 'member'

type Timestamps = {
  readonly createdAt: Date
  readonly updatedAt: Date | null
}

type BaseUser = {
  readonly id: number
  readonly email: string
  readonly avatar: string | null
  readonly metadata: Record<string, unknown>
}

type User = {
  readonly base: BaseUser
  readonly timestamps: Timestamps
  readonly role: Role | null
  readonly deletedAt: Date | null
}

// 1 way to say "nothing" · 3 states for `role`
// reuse by nesting — every field has one home
Why it matters: intersection merges BaseUser and Timestamps into User invisibly — fields appear from nowhere, and role alone can be 'admin', 'member', undefined, or missing. ShotScript keeps the reuse but as nested properties: user.base.email and user.timestamps.createdAt are explicit at the call site, every absent value is | null, and any is gone.

Async + error handling

TypeScript 
async function getUser(
  id?: number
): Promise<User | undefined> {
  if (!id) return undefined
  try {
    const res = await fetch(`/users/${id}`)
    if (!res.ok) throw new Error(
      `HTTP ${res.status}`
    )
    const data = await res.json() as any
    return data as User
  } catch (e) {
    console.error(e)
    return undefined
  }
}

// failure is invisible to callers · `as` silences the checker
ShotScript 
import { safeFetch, jsonParse } from 'shotscript/std'
import type { PromiseResult } from 'shotscript/std'

async function getUser(
  id: number
): PromiseResult<User> {
  const [res, fetchErr] = await safeFetch(
    `/users/${id}`
  )
  if (fetchErr !== null) return [null, fetchErr]
  return jsonParse<User>(await res.text())
}

// every failure is in the signature · no `as`, no `throw`
Why it matters: the left function can return undefined for "no id," undefined for "network failed," undefined for "bad JSON" — all indistinguishable. as User hides shape mismatches. The right version makes the input required, returns a PromiseResult tuple so every error path is typed, and uses jsonParse<User> instead of a cast.

Data + behaviour

TypeScript 
class UserService {
  private cache: Map<number, User> = new Map()

  constructor(private readonly db: Database) {}

  async findById(id: number) {
    const hit = this.cache.get(id)
    if (hit) return hit
    const user = await this.db.find(id)!
    this.cache.set(id, user)
    return user
  }
}

const svc = new UserService(db)
const u = await svc.findById(42)
ShotScript 
import { safeMapGet } from 'shotscript/std'

type UserService = {
  readonly db: Database
  readonly cache: Map<number, User>
}

async function findUserById(
  svc: UserService,
  id: number,
): PromiseResult<User> {
  const hit = safeMapGet(svc.cache, id)
  if (hit !== null) return [hit, null]
  const [user, err] = await svc.db.find(id)
  if (err !== null) return [null, err]
  svc.cache.set(id, user)
  return [user, null]
}

const svc: UserService = { db, cache: new Map() }
const [u, err] = await findUserById(svc, 42)
Why it matters: the class hides state behind private, leans on this, and uses ! to silence the checker on db.find. The ShotScript version makes the data shape explicit, the function callable in isolation, and forces the caller to handle the error tuple — no hidden control flow, no non-null assertion, nothing to mock around.
Install

One package. Five tools.

$ npm install --save-dev shotscript
ShotScriptLint — tsconfig plugin 
// tsconfig.json
{
  "compilerOptions": {
    "plugins": [{ "name": "shotscript/plugin" }]
  }
}
ShotScriptFmt — biome config 
// biome.json
{
  "extends": ["shotscript/fmt"]
}
ShotScriptTyping — tsconfig strict mode 
// tsconfig.json
{
  "extends": "shotscript/tsconfig/shotscript.json"
}
ShotScriptStd — stdlib import 
import { safeFetch, jsonParse } from 'shotscript/std'
import type { Result, PromiseResult } from 'shotscript/std'
