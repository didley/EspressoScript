shot is a subtractive superset of TypeScript. It removes features instead of adding them — applying Go's "one canonical way" philosophy to the TS/JS ecosystem.

The problem

Too many ways to write the same thing.

TypeScript lets you declare variables three ways, write functions four ways, handle errors five ways. Reading unfamiliar code is hard. Code review is harder. Static analysis is hardest.

shot's answer: a strict lint pass that enforces one canonical form. Every .shot file is valid TypeScript — so the full Deno ecosystem, type system, and tooling work unchanged. We maintain a list of rules, not a compiler.
no-throw
Errors are values — return ShotPromise<T, E> tuples. No hidden control flow, no class hierarchy.
no-arrow-function
Every function is named and grep-able. Callbacks become testable units.
no-ternary
If/else forces names onto branches. Nesting disappears.
no-class
Plain type + plain functions. No hidden state, no inheritance.
no-any / no-as
Type safety is not optional. No escape hatches.
no-interface
One way to define a shape: type.

Error handling

TypeScript
async function getUser(
  id: number
): Promise<User> {
  try {
    const res = await fetch(`/users/${id}`)
    if (!res.ok) throw new Error(
      `HTTP ${res.status}`
    )
    return res.json() as User
  } catch (e) {
    throw new Error(`getUser failed: ${e}`)
  }
}
shot
import { fetch, jsonParse } from "shot:std"
import type { ShotPromise } from "shot:std"

async function getUser(
  id: number
): ShotPromise<User> {
  const [res, err] = await fetch(`/users/${id}`)
  if (err !== null) {
    return [null, err]
  }
  return jsonParse<User>(await res.text())
}

// no throw · no try · no hidden control flow
Why it matters: thrown exceptions don't appear in function signatures. Callers have no idea a function can fail without reading its source — or its documentation, if any exists. ShotPromise<T, E> makes every failure path explicit in the type, enforced by the checker.

Custom error types

TypeScript
class ApiError extends Error {
  statusCode: number
  constructor(msg: string, code: number) {
    super(msg)
    this.statusCode = code
  }
}

async function getUser(
  id: number
): Promise<User> {
  const res = await fetch(`/users/${id}`)
  if (!res.ok) throw new ApiError(
    "not found", res.status
  )
  return res.json() as User
}

// caller doesn't know this throws
shot
type ApiError = {
  readonly message: string
  readonly statusCode: number
}

async function getUser(
  id: number
): ShotPromise<User, ApiError> {
  const [res, err] = await fetch(`/users/${id}`)
  if (err !== null) {
    return [null, { message: err.message, statusCode: 500 }]
  }
  if (!res.ok) {
    return [null, { message: "not found", statusCode: res.status }]
  }
  return jsonParse<User>(await res.text())
}

// caller sees ApiError in the signature
No class hierarchy needed. Custom error shapes are plain type declarations — no extends, no constructor, no this. The error type E in ShotPromise<T, E> can be anything: a plain type, or a discriminated union when a function has multiple failure modes. To add context when propagating, use wrapError(message, cause) from shot:std — the shot equivalent of Go's fmt.Errorf("context: %w", err).

Callbacks

TypeScript
const total = items
  .filter(x => x.active)
  .map(x => ({ ...x, score: x.score * 2 }))
  .reduce((acc, x) => acc + x.score, 0)

// inline logic · untestable · no names to grep
shot
function isActive(item: Item): boolean {
  return item.active
}
function doubleScore(item: Item): Item {
  return { ...item, score: item.score * 2 }
}
function sumScore(acc: number, item: Item): number {
  return acc + item.score
}

const total = items
  .filter(isActive)
  .map(doubleScore)
  .reduce(sumScore, 0)
Why it matters: named functions are testable in isolation, searchable with grep, and show up in stack traces. Anonymous arrow callbacks disappear the moment they fail.

Conditionals

TypeScript
const label = isAdmin
  ? (isSuperAdmin ? "Super Admin" : "Admin")
  : "User"

// nesting grows with every new role
shot
function roleLabel(
  isAdmin: boolean,
  isSuperAdmin: boolean,
): string {
  if (isSuperAdmin) {
    return "Super Admin"
  }
  if (isAdmin) {
    return "Admin"
  }
  return "User"
}
Why it matters: each branch has a name. Adding a new role means adding a clause, not untangling a nested expression. The complexity stays flat.

Data + behaviour

TypeScript
class UserService {
  private readonly db: Database

  constructor(db: Database) {
    this.db = db
  }

  async findById(
    id: number
  ): Promise<User | null> {
    // ...
  }
}

const svc = new UserService(db)
shot
type UserService = { readonly db: Database }

async function findUserById(
  svc: UserService,
  id: number,
): Promise<[User | null, Error | null]> {
  // ...
}

const svc: UserService = { db }
Why it matters: a type is data. A function is behaviour. There is no hidden state, no inheritance graph to trace, no this context to reason about. Both are independently testable.
Tooling

One command, four verbs.

shot's pipeline mirrors Go's: lint → type-check → run. The program never executes if the types are wrong.

terminal
# scaffold a project
$ shot init my-app

# type-check and lint
$ shot check src/

# format (delegates to deno fmt — zero config)
$ shot fmt

# run (lint → check → execute)
$ shot run src/main.shot

# test (lint → check → run *.test.shot)
$ shot test

shot is pre-v1 and open source. See the philosophy, language reference, and source on GitHub.
